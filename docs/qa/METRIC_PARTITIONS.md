# Daily metric partition acceptance

Scope: both raw samples and rollups must use PostgreSQL UTC daily range partitions, retain 14 rolling days, prepare the current/future window before writes and avoid parent-wide metric row deletion. No metric API or Vue change is needed.

- EF migration embeds fixed SQL and runs transactionally, preserving existing composite keys, rows and reader grants. It locks only the two metric tables (five-second lock / five-minute statement bounds), copies every existing day and verifies exact rows and counts before removing original heaps. The migrator must use the existing application table owner. Down preserves all still-retained rows and grants; it cannot resurrect data already expired by retention.
- Hourly/startup maintenance uses invoker permissions and a transaction advisory lock. Schema/table identifiers are constants. Each child must be a public ordinary leaf with the expected name and matching UTC bounds. Unmanaged/default/mismatched/colliding relations abort the transaction; drops never use CASCADE. PUBLIC receives no function execution permission.
- Whole expired days are dropped as partitions. Only the partial cutoff day needs indexed row cleanup, preserving the exact rolling 14-day boundary. Current and two future days are ready, including after a long downtime. Busy parallel maintenance returns a retry marker instead of blocking a sampling cycle.
- `validate_metric_partitions.py` runs the exact EF-generated scripts in a unique disposable database using its own non-login application-owner and read-only roles: empty migration chain, seeded upgrade/down/up, exact data, grants, null/warmup/leap/future values, duplicate keys, UTC offset and cutoff boundary, bounded/idempotent drops, unrelated/default/spoofed relations, long downtime, execution rights and concurrent lock skipping. Production DDL is forbidden in this script; scoped DB/roles are removed in finally.
- `validate_metric_partition_runtime.py` captures private count/digest watermarks before production migration and compares immutable windows afterward. It reads actual parent kinds, ownership, children, function rights and partition-pruned query plans. The digest is supporting evidence; full-row comparison inside the migration and isolated fixture checks provide the exact-copy proof.
- Existing PostgreSQL backup+checksum verification is required before production migration. The ordinary dev publisher performs EF migration; no manual production SQL or Docker daemon restart is needed. Metrics history, OIDC, container usage and internal maintenance schedule execution remain separate runtime regression gates.
